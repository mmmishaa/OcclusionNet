## Сеть и доступ

### SSH рвётся, хотя порт открыт

Ограничение SSH по адресу из `ifconfig.me` не работает, если вы за VPN со
split-tunnel: до российских адресов трафик идёт мимо туннеля, и облако видит
совсем другой источник.

Симптом обманчивый. Ожидаешь таймаут, а получаешь:

```
kex_exchange_identification: Connection closed by remote host
```

TCP-рукопожатие проходит, соединение рвётся до обмена версиями — выглядит как
проблема sshd, а не фильтрации. Мы потратили на это несколько итераций, потому
что параллельно молчали 80 и 443, и картина складывалась в «машина зависла».

Диагностика: откройте 22 порт в мир и проверьте. Заработало — дело в адресе.
Реальный адрес потом берите со стороны машины, `sudo ss -tnp | grep :22`,
а не с сервисов вроде ipify.

### Публичный IP меняется при каждом запуске

У ВМ динамический адрес: остановили и запустили — он другой. Поэтому в
`/etc/cron.d/duckdns` стоит обновление записи каждые 5 минут. DuckDNS при
запросе без параметра `ip` подставляет адрес источника, так что скрипту не надо
знать свой адрес.

## cloud-init

### Caddy: пакет ставится до конфига, не наоборот

Нельзя класть `/etc/caddy/Caddyfile` через `write_files`. Пакет `caddy`
поставляет собственный конфиг по этому пути, dpkg видит чужой файл на месте
своего и задаёт интерактивный вопрос. stdin у cloud-init закрыт:

```
end of file on stdin at conffile prompt
dpkg: error processing package caddy (--configure)
```

Пакет остаётся ненастроенным, порты 80 и 443 молчат, при этом ClearML работает —
и непонятно, что сломалось. Правильный порядок: `apt-get install caddy`, потом
запись конфига в `bootstrap.sh`. Плюс `-o Dpkg::Options::=--force-confold` на
случай, если файл всё же окажется на месте.

### Экранирование в templatefile

`templatefile` перехватывает доллар и процент **только** перед фигурной скобкой.
Отсюда две ошибки, которые мы сделали обе:

**Лишнее удвоение.** `$$(...)` и `$$VAR` не нужны — это не шаблонные
последовательности. После рендера остаётся `$$`, а в bash это PID процесса:

```
/usr/local/bin/bootstrap.sh: line 14: syntax error near unexpected token `('
```

**Доллар с фигурной скобкой в комментарии.** Шаблон не различает код и
комментарии. Строка вида «перехватывает только "${" и "%{"» ломает рендер:

```
Invalid multi-line string; Quoted strings may not be split over multiple lines
```

### Проверять шаблон локально, а не в облаке

Каждая такая ошибка иначе стоит пересоздания ВМ и девяти минут, а видна только в
серийной консоли — кольцевом буфере, который вытесняется логами Docker. Цикл
проверки за секунды:

```bash
# отрендерить templatefile во временном модуле, затем
grep -n '\$\$' rendered.yaml          # лишние удвоения
python3 -c "import yaml; yaml.safe_load(open('rendered.yaml'))"
bash -n извлечённый_скрипт.sh
```

## OpenTofu

### Провайдер Yandex в реестре OpenTofu отстаёт

В `registry.opentofu.org` максимум 0.127, в реестре Terraform — 0.220. Нужные
ресурсы (DataSphere, Lockbox) появились позже, поэтому источник указан полностью:

```hcl
yandex = {
  source  = "registry.terraform.io/yandex-cloud/yandex"
  version = "~> 0.220"
}
```

### Terraform молча врёт про файлы .tofu

Расширение `.tofu` понимает только OpenTofu с 1.8. Terraform такие файлы не
видит, но **ошибки не выдаёт** — считает каталог пустым и рапортует успех:

```bash
terraform validate   # Success! The configuration is valid.
```

Проверено на заведомо битом HCL: `tofu` ругается, `terraform` доволен. Отличить
можно так:

```bash
tofu providers      | grep -c 'provider\['   # 2
terraform providers | grep -c 'provider\['   # 0
```

### terraform.tofuvars не существует

Файл переменных остаётся `terraform.tfvars`. Переименование в `.tofuvars`
автозагрузка не подхватывает, и обязательные переменные оказываются
незаданными.

### Планы содержат секреты

`tofu plan -out` сохраняет значения переменных, включая пароли и токены. Это
zip-архив, так что `grep` и `strings` по нему ничего не находят и создают ложное
ощущение безопасности. `*.tfplan` в `.gitignore`.

## Yandex Cloud: неочевидные ограничения API

### storage.editor не хватает для настройки бакета

Роль позволяет работать с объектами, но не менять конфигурацию бакета.
Версионирование и lifecycle требуют `storage.admin`:

```
Error: handling versioning: AccessDenied, status code: 403
```

Бакет при этом создаётся — падает уже следующий вызов.

### Удержание снапшотов: либо количество, либо период

Если задать и `snapshot_count`, и `retention_period`, API принимает только
первое и не возвращает второе. Терраформ каждый раз видит недостающее поле:

```
~ resource "yandex_compute_snapshot_schedule" "daily" {
    + retention_period = "168h"
```

Вечный дрейф в плане на пустом месте. Оставлять что-то одно.

### image_family в initialize_params не существует

Образ берётся через data-source:

```hcl
data "yandex_compute_image" "ubuntu" {
  family = "ubuntu-2404-lts"
}
```

### Бюджетов нет ни в провайдере, ни в CLI

`yandex_billing_budget` в провайдере отсутствует (есть только
`yandex_billing_cloud_binding`), группы `yc billing` в CLI тоже нет. Алерт
заводится руками в консоли.

## DataSphere

### Ролей нужно две, и обе на сообществе

Права распространяются вниз по иерархии, поэтому роль на сообществе действует на
все проекты внутри, включая созданные позже. Привязывать людей к конкретному
проекту не нужно — иначе каждый новый проект потребовал бы правки Terraform.

Но роли про разное:

| Роль | Что даёт |
|---|---|
| `datasphere.communities.developer` | создавать проекты, публиковать ресурсы |
| `datasphere.community-projects.developer` | работать внутри проектов: IDE, вычисления |

С одной первой человек числится в сообществе, но в проект не попадает — ровно
это мы и наблюдали.

### Имена ролей: множественное число и точка

`datasphere.community-developer` не существует. Ошибка вылезает **только на
apply**, плану она не видна, и падает он уже после создания community — то есть
состояние остаётся частично применённым. Проверять заранее:

```bash
yc iam role list | grep datasphere
```

### Баланс проекта при создании равен нулю

API создаёт проект с `limits.balance = 0`, и ячейки не запускаются вообще.
Диагностируется плохо: в интерфейсе это молчаливый отказ, а не сообщение об
исчерпанном лимите, и выглядит как поломка ядра.

Поле есть в провайдере и управляется переменной `datasphere_balance`. По
умолчанию она `null` — атрибут `optional+computed`, поэтому выставленное
руками значение apply не трогает. Проверяется так:

```bash
tofu plan -var datasphere_balance=1000000 | grep -A4 datasphere_project
```

Баланс — это запас единиц, а не скорость расхода. Ограничение скорости — это
`max_units_per_hour`, и путать их не стоит: можно иметь щедрый баланс и всё
равно упереться в часовой потолок.

### Подключение внешних IDE провайдером не настраивается

Настройки «Режим работы проектов» в ресурсе нет. Провайдер `~> 0.220` отдаёт в
`settings` только шесть полей, и среди них ничего про IDE:

```bash
tofu providers schema -json \
  | jq '.provider_schemas[].resource_schemas.yandex_datasphere_project.block.attributes.settings'
```

Группы `yc datasphere` в CLI тоже нет — проверяется одной командой
`yc datasphere --help`, которая молча печатает общую справку вместо ошибки.
Значит, включать VS Code руками и повторять после каждого пересоздания проекта.

### Проект намеренно не привязан к подсети

`subnet_id` не задан. Привязка означает, что вычислениям нужен выход в интернет
через NAT-шлюз — за pip, веса моделей и за наш же ClearML, — а это отдельные
деньги за шлюз и трафик. Без `subnet_id` проект работает в управляемой сети
Yandex, где интернет уже есть, а до ClearML достучится по публичному адресу с
TLS. Привязывать стоит только ради приватных ресурсов, которых у нас нет.

## Экономика

### Где держать датасеты решает не удобство, а география вычислений

Colab и Kaggle находятся снаружи облака. Скачивание из Object Storage им идёт
платным исходящим трафиком, а сессии рвутся каждые 9–12 часов и стартуют с
чистой машины — датасет качается заново при каждом рестарте. При десятках
гигабайт и нескольких перезапусках в день трафик легко перегоняет стоимость
самой ВМ.

DataSphere внутри облака, трафик до бакета в том же регионе так не
тарифицируется. Поэтому рекомендация прямо противоположная, и бакетов два:
у артефактов ClearML lifecycle с автоудалением через 30 дней, датасетам такое
противопоказано.

### Обрывки многочастевых загрузок тарифицируются

Незавершённые multipart-загрузки занимают место, но не показываются в списке
объектов. Colab рвёт сессию посреди заливки чекпойнта регулярно, поэтому в обоих
бакетах стоит `abort_incomplete_multipart_upload_days`.

### Главные рычаги для недельного пилота

Выключенная ВМ не тарифицируется вообще, платится только диск. Гарантированная
доля vCPU 20% вместо 100% — сервер почти всегда простаивает, пики закрывает
burst. Прерываемая ВМ скидку даёт, но принудительный стоп каждые 24 часа ради
пары сотен рублей того не стоит.

## Смена сгенерированных значений на живом стенде

Имя бакета и пароль администратора генерирует провайдер `random`. Менять их у
работающего стенда нельзя: cloud-init запекает имя бакета в
`/opt/clearml/config/clearml.conf`, а пароль в `apiserver.conf` — оба на этапе
загрузки. На инстансе стоит `ignore_changes` для user-data, поэтому ВМ не
пересоздастся, и ClearML продолжит писать артефакты в бакет, которого больше
нет, — молча. Менять только вместе с:

```bash
tofu apply -replace=yandex_compute_instance.clearml
```

## Домены

### DuckDNS резолвит вложенные поддомены

ClearML требует три имени — `app.`, `api.`, `files.`. DuckDNS даёт одно, но
резолвит любые имена под ним в тот же адрес. В FAQ это не документировано,
проверено эмпирически на шести существующих именах и затем на своём. Проверить:

```bash
dig +short app.вашеимя.duckdns.org
```

### Домены freedns.afraid.org не подходят

Они не входят в Public Suffix List, поэтому Let's Encrypt считает весь общий
домен одним и тем же — лимит 50 сертификатов в неделю делится со всеми
пользователями. У `mooo.com` порядка 400 000 поддоменов, и лимит там обычно уже
выжжен, в том числе намеренно. `duckdns.org`, `ddns.net`, `hopto.org`, `zapto.org`
в PSL входят, у них лимит считается на ваше имя.
